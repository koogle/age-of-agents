Müller-Brockmann’s grid system, applied to Age of Agents

Research and design proposal · 4 October 2026. This is a presentation study of the current Rust interface, not a deployed replacement.

What the research supports

In his 1995 interview, Müller-Brockmann describes the grid as an organisational system for making a message easier to read. He puts the clear identification of priorities, legibility, proportion and meaningful colour before visual novelty. He also explicitly permits individual variations and says his earlier defence of rules had softened. A grid therefore requires judgment about the content; it does not supply the answer automatically.

The publisher describes the 1981 handbook as a step-by-step treatment of grids with 8–32 fields. Its sample spreads show margin comparisons, modular layouts, and a poster beside its underlying structure. Those fields should not be confused with a mandatory number of screen columns. The small online sample images let me inspect composition, but not reliably read all captions. I did not read the full 176-page book.

The museum example, Musica Viva (1958), uses a rotated organisation, deliberate empty space, and grouped type. This demonstrates that a grid can support an expressive composition. A game HUD nevertheless needs stable orientation and rapid scanning; rotating its controls would not serve that purpose.

The five-part Mark Boulton series develops grids through related proportions, content areas, hanging lines, gutters and adaptation to changing type and viewport sizes. Miner and Rutter explain vertical rhythm through line height and spacing. Their older implementation examples are historical references, not current browser or accessibility guidance. The modern UI article distinguishes column, modular and baseline grids and argues that content should determine the system.

Source criticism matters: the 2017 UI article incorrectly captions the handbook as 1961; the publisher dates it to 1981. I use the publisher’s date. I also do not adopt broad claims about the golden ratio guaranteeing beauty or usability. There is no task-specific evidence for those claims here.

Reading record

  1. Eye, “Reputations: Josef Müller-Brockmann”, Yvonne Schwemer-Scheddin, Winter 1995. Full online interview read. Primary source for priorities, legibility, variation, typography and self-criticism.
  2. Niggli, Grid Systems in Graphic Design. Publisher description and four sample spreads inspected. Authoritative book metadata; not a substitute for the full text.
  3. MoMA collection and Musica Viva, 1958. Collection record read and poster image inspected for composition and hierarchy.
  4. Design Is History, Müller-Brockmann. Short biography read for historical context, not used as detailed grid instruction.
  5. Mark Boulton, Five simple steps to designing grid systems, all five parts read: 1: subdivisions, 2: related proportions, 3: web constraints, 4: fixed grids, 5: adaptive grids.
  6. Wilson Miner, Setting Type on the Web to a Baseline Grid. Read for alignment, leading, images, borders and exceptions.
  7. Richard Rutter, Compose to a Vertical Rhythm. Read for the relationship between type size, line height and space around headings.
  8. Diogo Terror, Lessons From Swiss Style Graphic Design. Read for functional whitespace, semantic grouping and typography. Its general historical claims are secondary evidence.
  9. Nick Babich, Building Better UI Designs With Layout Grids. Read for contemporary grid anatomy, content-led column choice, responsive adaptation and testing.
  10. W3C, Target Size (Enhanced) and Reflow. Relevant guidance reviewed for touch sizes and content reflow. 44×44 CSS pixels is the enhanced AAA target criterion, not the universal AA minimum. The prototype’s targets use at least 44px; no whole-product accessibility conformance is claimed.

This is a bounded review of relevant, accessible sources, not a claim to have exhausted everything published online. Search access was inconsistent; sources were read directly. No paywall or restricted book access was bypassed.

Application to the game

The user clarified that the goal is to improve placement and relationships while retaining the game's character. Artwork may change if that character survives. The current study therefore preserves the actual Rust-rendered medallions, pills, font, sizes and content and only translates their positions. It supersedes the first panel-based concept.

The 24px inset and 44px speed pitch are proposed measurements for this viewport, not rules attributed to Müller-Brockmann. No generic 8- or 12-column dashboard system is imposed on the island. A useful HUD grid is primarily a system of edges, centers, baselines and distances between functional groups.

Mobile placement study

The follow-up uses an actual 390×844 browser-local viewport at DPR 2. It retains the current art, labels and medallion sizes. The command strip reflows from multiple rows beside the globe into one centered bottom row; its existing parchment background is resized with the same corner treatment. The selection pill sits 12 logical pixels above that strip. A 96px globe and a straight row of speed coins form a group above the selection on the right. Utilities and stocks receive small inset adjustments. The smaller globe is a proposed size change, explicitly distinct from the desktop translation-only study.

Compare current and proposed mobile states: overview, town center, build categories and Town submenu. This is visual evidence at one phone width, not functional touch validation: renderer instrumentation does not relocate hit regions. Narrower widths, device safe areas, enlarged text, crowded stock lists and full queues remain open. The original small labels are preserved and should be reconsidered before shipping.

Art direction constraint

Preserve warm parchment, gold rims, painted Greek motifs, soft translucent pills, round medallions and generous gameplay space. Artwork can be refined or replaced when it strengthens this language. A new font, broad rectangular panels and a flat dashboard treatment are not part of this proposal.

What this deliverable is

The comparison captures the checked-in WebGL client in browser-local mode. Browser instrumentation translates HUD vertices for screenshots; it does not change shipped code, asset files, game state on the hosted server, or command hit regions. Consequently the images are a placement study, not an interactive game implementation. The comparison viewer switches between actual current and proposed screenshots.

First pass is scoped to a 1440×900 desktop viewport with town-center, category and build-submenu states. Mobile, crowded stocks, long labels, full production queues and different display scales need their own layout checks. No claim of phone usability or improved measured usability is made. Small current targets remain small; shipping changes should enlarge invisible hit regions and verify keyboard and touch access without necessarily enlarging the artwork.

Implementation and verification boundary

A shipping layout would derive both draw positions and hit regions from the same geometry in crates/client/src/hud/layout.rs, keeping typed actions and current catalog behavior. This prototype does not alter simulation, persistence or deployment. The capture script is capture-placement.cjs; it requires the local static server on port 8001, Playwright and Chromium. Its geometric translations are narrowly scoped to these desktop screenshots, not a reusable HUD engine.

The viewer checks image loading and before/after, menu-state and guide toggles. Actual Rust, native, touch and deployment verification are not completed because no runtime change is being shipped. The central design question is whether the new relationships improve the existing composition while retaining its lightness.
